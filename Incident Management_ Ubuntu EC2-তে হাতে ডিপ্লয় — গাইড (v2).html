Incident Management: Ubuntu EC2-তে হাতে ডিপ্লয় (Docker ছাড়া)

React, Express আর PostgreSQL দিয়ে বানানো একটা অ্যাপ নিজের হাতে একটা আসল সার্ভারে চালু করবেন: SSH দিয়ে ঢুকে, apt দিয়ে ইনস্টল করে, systemd আর Nginx দিয়ে। প্রতিটা ধাপে আছে কী করবেন, কেন, আর ভিডিওতে কী বলবেন।

ZIP পরিষ্কার করা হয়েছে, আর আমরা Ubuntu 26.04 ব্যবহার করছি আপনার ZIP-এর (Incident_Management_Project.zip) ভেতরে দুটো অপ্রয়োজনীয় জিনিস ছিল। একটা হলো প্রজেক্টের হুবহু আরেকটা কপি, প্রজেক্টের ভেতরেই একই নামের ফোল্ডারে। আরেকটা হলো ট্রেনারের GitHub রিপোর (Nure/...) .git ইতিহাস। আমি এগুলো বাদ দিয়ে একটা পরিষ্কার ZIP বানিয়েছি, নাম incident-management-ubuntu-ec2.zip, যেটা নির্দেশনার নামের সাথে হুবহু মেলে। কোডের একটা লাইনও বদলাইনি। এই ZIP-টাই ব্যবহার করবেন।

১. আপনার মানগুলো বসান

মান বসালে নিচের সব PowerShell আর ssh কমান্ড নিজে থেকেই তৈরি হয়ে যাবে।

মানগুলো শুধু আপনার ব্রাউজারে থাকে। Public IP প্রতিবার instance Stop করে আবার Start করলে বদলে যায়, তাই সতর্ক থাকবেন।

২. ভিডিও রেকর্ডিং প্ল্যান

এই লাবে স্ক্রিনে কখনো আনবেন না
  • .pem ফাইলের ভেতরের লেখা, আর Part G-তে বানানো deploy key-র private অংশ (bongodev_incident_deploy, যার শেষে .pub নেই)। যে কেউ এটা দেখলে আপনার সার্ভারে ঢুকতে পারবে।
  • backend/.env-এর ভেতরের লেখা। ক্যামেরায় cat backend/.env চালাবেন না, কারণ এতে ডাটাবেসের পাসওয়ার্ড আছে। স্ক্রিপ্টগুলো নিজে পাসওয়ার্ড প্রিন্ট করে না, এটা আমি মিলিয়ে দেখেছি।
  • GitHub-এ Secret পেস্ট করার মুহূর্ত। পেস্ট করার সময় বক্সে key-টা দেখা যায়, তাই তখন রেকর্ডিং pause করুন।
BLUR করবেন: কনসোলের উপরের ডানদিকে Account ID। আপনার বাসার IP-ও blur করবেন, যেটা Security group-এর "My IP" রুলে দেখা যায়।
দেখালে সমস্যা নেই: EC2-র public IP (লাব শেষে মুছে যাবে), .pub public key, host key fingerprint।

৩. আর্কিটেকচার: কোন অংশ কী করে

প্রতিটা অংশের কাজ Nginx সার্ভারের "সদর দরজা", বাইরের দুনিয়ার সাথে একমাত্র এটাই কথা বলে। কেউ / চাইলে Nginx React-এর তৈরি HTML, JS আর CSS ফাইল ডিস্ক থেকে সরাসরি পাঠিয়ে দেয়। /api/... চাইলে অনুরোধটা ভেতরে Node-এর কাছে পাঠায়। এভাবে মাঝখানে বসে অনুরোধ এগিয়ে দেওয়াকে বলে reverse proxy।
Express (Node.js) হলো ব্যবসার নিয়ম: incident বানানো, বদলানো, মোছা। এটা শুধু 127.0.0.1-এ শোনে, মানে সার্ভারের ভেতর থেকেই শুধু এর কাছে পৌঁছানো যায়।
PostgreSQL ডেটা স্থায়ীভাবে রাখে। এটাও শুধু ভেতরের জন্য, port 5432 বাইরে খোলা নেই।
systemd হলো Ubuntu-র "সার্ভিস ম্যানেজার"। Node crash করলে এটা আবার চালু করে, আর সার্ভার reboot হলেও Node নিজে থেকে চালু হয়।
ভিডিওতে বলুন (S0)"আগের লাবে GitHub Actions দিয়ে সার্ভার বানিয়েছিলাম। আজ উল্টো দিক থেকে দেখব: একটা চালু সার্ভারে আসল অ্যাপ নিজের হাতে বসাব। কোনো Docker নেই, প্রতিটা অংশ সরাসরি Ubuntu-তে চলবে। অটোমেট করার আগে জানা দরকার কী কী অটোমেট করছি। বাইরের দুনিয়ার জন্য খোলা শুধু port 80। Node আর ডাটাবেস সার্ভারের ভেতরে লুকানো, শুধু Nginx তাদের সাথে কথা বলে।"

Part A — EC2 লঞ্চ করুন

Step 1

Ubuntu EC2 লঞ্চ করুন

▶
  1. Region us-east-1 বেছে নিন। তারপর EC2 → Instances → Launch instances খুলুন।
  2. Name দিন bongodev-incident-ubuntu।
  3. AMI: Quick Start থেকে Ubuntu, Architecture 64-bit (x86)। অ্যাসাইনমেন্টে বলা আছে 24.04 LTS, তবে এখন Quick Start-এর ডিফল্ট 26.04 LTS। আমরা 26.04 ব্যবহার করছি, তাই Step 3b-এ স্ক্রিপ্টের ভার্শন পরীক্ষাটা একটু বদলাতে হবে। Amazon Linux নেবেন না।
  4. Instance type: t3.small (2 GiB RAM)।
  5. Key pair: আপনার key-র নাম asifiqrawave, ফাইল Downloads\asifiqrawave.pem। নতুন বানালে Type ED25519 আর Format .pem দেবেন (.ppk না)। Instance-এর Details ট্যাবে "Key pair assigned at launch"-এ এই নামটাই থাকতে হবে।
  6. Network settings → Edit খুলুন। VPC থাকবে default, Subnet যেকোনো একটা, আর Auto-assign public IP = Enable।
  7. Create security group বেছে নিন। নাম দিন bongodev-incident-sg, আর এই দুটো রুল যোগ করুন:
    TypePortSource
    SSH22My IP। ISP একাধিক IP ব্যবহার করলে 103.174.150.0/24-এর মতো একটা ছোট পরিসর দিন, নিচের সতর্কবার্তা দেখুন।
    HTTP80Anywhere-IPv4 (0.0.0.0/0)
  8. Storage: 20 GiB gp3।
  9. Launch instance চাপুন। Instance state Running হলে Public IPv4 address কপি করে পেজের উপরে বসান।
কেন এই সেটিংগুলো Ubuntu, Amazon Linux না: স্ক্রিপ্টগুলো apt ব্যবহার করে আর শুরুতেই পরীক্ষা করে নেয় যে সিস্টেম Ubuntu 24.04 কিনা। অন্য কিছু হলে থেমে যাবে।
t3.small: React build (Vite) চলার সময় বেশ মেমরি লাগে। 1 GiB-এর t3.micro-তে build মাঝপথে "Killed" হয়ে যেতে পারে। t3.small free tier-এ পড়ে না, তবে খরচ খুব কম, আর কাজ শেষ হলেই terminate করবেন।
ED25519 key: RSA-র চেয়ে আধুনিক, ছোট আর দ্রুত। .pem হলো private key। AWS এর কোনো কপি রাখে না, তাই হারালে এই সার্ভারে আর ঢুকতে পারবেন না।
Security group: port 22 শুধু আপনার IP থেকে খোলা, তাই অন্য কেউ SSH চেষ্টাও করতে পারবে না। 5000 আর 5432 খুলবেন না। Node আর DB-কে বাইরে থেকে কারো দেখার দরকার নেই, তাদের সাথে কথা বলে শুধু Nginx।
আমাদের অভিজ্ঞতা: "My IP" কাজ না করলেআমাদের ক্ষেত্রে checkip একেকবার একেক IP দেখাচ্ছিল (.98, .99), আর AWS আসলে যে IP দেখছিল সেটা আবার এর কোনোটাই ছিল না। ফলে /32 আর /31 দুটোতেই Connection timed out এসেছিল। এভাবে খুঁজে পেয়েছি: SSH সাময়িকভাবে 0.0.0.0/0 করে ঢুকলাম, ভেতরে echo $SSH_CLIENT চালিয়ে AWS যে IP দেখছে সেটা বের করলাম, তারপর সাথে সাথে রুলটা সেই IP বা ছোট পরিসরে আটকে দিলাম। কোথায় সমস্যা, সেটা আলাদা করতে Test-NetConnection github.com -Port 22 কাজে লাগে: True এলে বোঝা যায় ISP port 22 আটকায় না।
ভিডিওতে বলুন"Security group হলো সার্ভারের firewall। দুটো দরজা খোলা রাখছি: 80 সবার জন্য, যাতে যে কেউ ওয়েবসাইট দেখতে পারে, আর 22 শুধু আমার IP থেকে, যাতে শুধু আমি সার্ভারে ঢুকতে পারি। ডাটাবেসের দরজা 5432 ইচ্ছা করেই বন্ধ রাখছি।"

কেন icaclsSSH খুব কড়া একটা নিয়ম মানে: private key অন্য কেউ পড়তে পারলে সেটা ব্যবহারই করবে না, আর এরর দেবে "UNPROTECTED PRIVATE KEY FILE"। Mac বা Linux-এ এটা ঠিক করতে chmod 400 চালাতে হয়। Windows-এ একই কাজ করে icacls। প্রথম লাইন ফোল্ডার থেকে আসা উত্তরাধিকার-সূত্রের permission মুছে দেয়, আর দ্বিতীয় লাইন শুধু আপনাকে পড়ার অনুমতি দেয়।


কেন "yes" জিজ্ঞেস করেপ্রতিটা সার্ভারের নিজস্ব একটা host key থাকে, যা দিয়ে সার্ভারকে চেনা যায়। প্রথমবার ঢোকার সময় আপনার কম্পিউটার এটা মনে রেখে দেয় (known_hosts)। পরে কেউ মাঝখানে বসে নকল সার্ভার সাজালে key মিলবে না, আর SSH সতর্ক করবে। Part G-তে এই একই ধারণা GitHub-এর জন্য ব্যবহার করব।

Step 3b
স্ক্রিপ্টে Ubuntu 26.04 অনুমতি দিন
▶


প্রতিটা স্ক্রিপ্ট শুরুতেই পরীক্ষা করে সার্ভারটা ঠিক 24.04 কিনা, আর না হলে Ubuntu 24.04 required বলে থেমে যায়। আমাদের সার্ভার 26.04, তাই এই একটা শর্তে 26.04 যোগ করছি। এর বাইরে কোডের আর কিছু বদলাচ্ছি না।


EC2-তে, প্রজেক্ট ফোল্ডারের ভেতরে চালান:


grep -E '^(PRETTY_NAME|VERSION_ID)=' /etc/os-release
sed -i "s/\"\$VERSION_ID\" == '24.04'/( \"\$VERSION_ID\" == '24.04' || \"\$VERSION_ID\" == '26.04' )/" scripts/*.sh
grep -n "VERSION_ID" scripts/*.sh


শেষ কমান্ডের আউটপুটে ৬টা লাইন আসবে, প্রতিটায় লেখা থাকবে "$VERSION_ID" == '24.04' || "$VERSION_ID" == '26.04'। আমি এই কমান্ড আগে পরীক্ষা করে দেখেছি: সব স্ক্রিপ্টের syntax ঠিক থাকে, আর 26.04-এ পরীক্ষাটা পাস করে।


এটা কেন ঠিক আছে, আর কোথায় ঝুঁকি
স্ক্রিপ্টের এই পরীক্ষা একটা সুরক্ষা (fail fast): অচেনা OS-এ চালালে ভুল প্যাকেজ বসে যেতে পারত, তাই আগেই থেমে যায়। 26.04 আর 24.04 দুটোই Ubuntu LTS, একই apt, systemd আর Nginx-এর ফোল্ডার কাঠামো। তাই স্ক্রিপ্টের বাকি অংশ একইভাবে কাজ করার কথা।

পার্থক্য যা থাকবে: PostgreSQL-এর ভার্শন নতুন হবে, কারণ 26.04-এর নিজস্ব ভাণ্ডারে নতুনটা আছে। Node.js আসবে NodeSource থেকে, তাই সেটা 24-ই থাকবে।

অ্যাসাইনমেন্টের দিক থেকে: চেকলিস্টে লেখা "Ubuntu 24.04"। তাই README-তে পরিষ্কার লিখে দেব যে 26.04 ব্যবহার করেছি, আর কেন, আর কী বদলেছি। কোনো ধাপে অপ্রত্যাশিত এরর এলে সবচেয়ে নিরাপদ সমাধান হলো 24.04 দিয়ে নতুন instance।


ভিডিওতে বলুন"স্ক্রিপ্ট আমার সার্ভারে চলতে রাজি হয়নি, কারণ এটা নতুন Ubuntu 26.04। এটা ভালো লক্ষণ: স্ক্রিপ্ট আগেই OS যাচাই করে নেয়। আমি শুধু ভার্শন পরীক্ষার শর্তে 26.04 যোগ করছি, বাকি কোড অপরিবর্তিত।"

  2. backend/.env-এ সেটা লেখে, আর permission দেয় 600, মানে শুধু ubuntu ইউজার পড়তে পারবে। .gitignore-এ .env আছে, তাই ভুল করেও এটা GitHub-এ যাবে না।

Node-কে জোর করে মেরে ফেলা হলো। কিন্তু ৩ সেকেন্ড পরে systemd নিজেই আবার চালু করে দেবে (Restart=on-failure), আর status-এ নতুন PID আর "active (running)" দেখা যাবে।


তিনটা প্রশ্নের উত্তর (নির্দেশনায় চাওয়া)
Backend crash করলে কে চালু করে? systemd, কারণ service ফাইলে Restart=on-failure আর RestartSec=3 দেওয়া আছে।

Backend 127.0.0.1:5000-এ কেন শোনে? যাতে শুধু Nginx তার কাছে পৌঁছাতে পারে। বাইরের সব অনুরোধ Nginx হয়ে আসবে, যেখানে পরে TLS, rate limit বা log যোগ করা যায়।

PostgreSQL ইন্টারনেট থেকে কেন খোলা নয়? ডাটাবেস সবচেয়ে মূল্যবান জিনিস। বাইরে খোলা থাকলে পুরো দুনিয়ার bot পাসওয়ার্ড অনুমান করার চেষ্টা করবে। অ্যাপ আর DB একই মেশিনে, তাই বাইরে খোলার দরকারই নেই।






Part G — (ঐচ্ছিক) GitHub Actions দিয়ে অটো-ডিপ্লয়


শুরুর আগে: সার্ভার চালু রাখুনPart G-র জন্য এই একই EC2 চালু থাকতে হবে। তাই মূল লাবের সব স্ক্রিনশট (১–১২) নেওয়া হয়ে গেলে terminate না করে এখানে আসুন। এই workflow নতুন সার্ভার বানায় না, চালু থাকা সার্ভারে শুধু নতুন কোড পাঠায়।


একটা বড় সমস্যা আছে, আগে জেনে রাখুন
GitHub-এর runner SSH দিয়ে আপনার EC2-তে ঢুকবে। কিন্তু security group-এ port 22 খোলা শুধু আপনার বাসার IP-র জন্য, আর GitHub runner-এর IP প্রতিবার বদলায়। ফলে deploy ধাপে Connection timed out আসবে। নির্দেশনায় পরিষ্কার বলা আছে, 22 সবার জন্য খুলে দেবেন না (0.0.0.0/0)।


সমাধান আমরা Step 14-এ এসে একসাথে ঠিক করব। আমার পছন্দের উপায় হলো লাব ২-এর OIDC কাজে লাগানো: workflow চলার সময় শুধু ওই মুহূর্তের runner IP-র জন্য ২২ খুলবে, আর কাজ শেষ হলে আবার বন্ধ করবে। এর জন্য deploy.yml-এ দুটো ধাপ যোগ করতে হবে।
